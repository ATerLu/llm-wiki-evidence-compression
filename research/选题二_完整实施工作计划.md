## 二、三个研究问题与边界

**RQ1：在同一候选池和 token 预算下，保护更名／别名、指代前件等必要关系，能否减少压缩断链并提高答案质量？** 与独立句级选择、调优的相邻句补全、Provence 等方法比较。依赖关系识别错了也可能有害，因此要同时测误保留与漏保留。

**RQ2：在总存储额度受限时，提前保存哪些长短证据表示，能否比普通缓存和固定摘要更划算？** “证据视图”指带原文跨度及依赖信息的可复用中间结果，不等同于具有严格查询等价保证的关系数据库视图。

**RQ3：在线如何选择短视图、扩展视图或原文回退，才能在接近的质量下减少完整查询时间？** 以实际执行代价校准策略，避免选择器本身过慢。

初版处理两类关系：明确别名／更名、明确指代前件。条件限定作为后续扩展。跨文档实体同一性证据不足时只作软关联；共享名字或主题不等于同一实体。所谓“依赖保持”只针对已识别关系，不预先保证语义完整或答案正确。

Wiki 在本题中是**可复用的来源与关系索引**，可用 SQLite 表与可选 Markdown 页面呈现。需要与“直接从原文建立同类关系”对照；若 Wiki 层没有额外收益，就把贡献如实表述为通用 RAG 上下文与数据管理方法。

本轮核验的是入口与说明，未执行数据包下载和全量解析。下载时记录文件名、URL、获取时间、字节数、SHA-256、许可和记录数。HotpotQA 为 CC BY-SA 4.0，MuSiQue 为 CC BY 4.0；公开派生数据时沿用相应归属与许可要求。

### 4.2 划分与逐级扩大

**开发阶段使用官方 train，最终冻结评估使用官方 dev。** 原始 dev 不再兼作无限次调参集。先在 train 内按问题族／重复问题分组固定划分：每个数据集抽 100 题作冒烟检查、500 题作方法开发、另留 500 题作开发验证；三者尽量互斥，样本 ID 和随机种子提前落盘。若 MuSiQue 问题共享相同分解组成，应以组合家族分组，避免近似重复跨划分。

第一轮冻结验证可各用 500 题，主要决定是否继续投入。正式主表目标为**每个数据集至少 1,000 个预先抽取的问题**，按问题类型／跳数分层；资源允许再扩至完整官方 dev。子集结果必须标记“冻结子集”，不得称为完整基准结果。最终样本量根据开发验证中的配对差异方差估算；1,000 题并不自动保证能检出 1 个 F1 点的差异。

只读语料可以包含评测时允许访问的原始文档，这符合固定知识库设定；**离线索引不允许读取测试问题、答案、支持标签或分解链来选择视图**。若语料取自全部候选段落的并集，应明确这是限定语料设置，所有方法得到同一文档集合，不能包装为全维基检索。测试语料是否参与离线编译要在协议中写明。

### 4.3 统一数据格式与防泄漏

建议将可用输入与评测标签写入不同文件：

- `corpus.jsonl`：文档 ID、版本、标题、原文、句子／字符跨度及来源。
- `queries.jsonl`：问题 ID、问题文本、允许的候选文档 ID；不含答案与支持标签。
- `labels.jsonl`：标准答案、答案别名、支持事实、跳数／问题类型，仅评测模块加载。
- `splits.json`：开发、验证、冻结评测 ID，以及划分种子和规则。
- `workloads.jsonl`：问题族 ID、到达顺序、重复／改写类型、来源版本事件。

HotpotQA 的支持事实以标题与句序对应；同名标题但文本不同应按内容哈希和版本区分，不能仅按标题合并。MuSiQue 需要保留原始段落索引，再建立自己的句子跨度映射。分句、空格规范化和标题拼接后仍应能回到原文。

MuSiQue 官方明确提示源单跳数据可能与 dev／test 组合重叠，并提供相关 ID。若后续用这些源数据训练任何模块，要进行排除；初版使用冻结模型也应披露可能的预训练污染，不能声称完全没有污染。[说明](https://github.com/StonyBrookNLP/musique#data)

### 4.4 人工依赖标注

先对自然随机抽取的 200 题标注：关系类型、被解释句、必要解释跨度、是否确有必要、候选池是否含该跨度、压缩后是否保留。可以另外构建定向困难样本集，但必须与随机子集分开统计，不能以人工挑选的失败案例代表整个数据集。

建议两人独立标注至少 50 题并复核分歧，报告类别一致率与跨度一致性。若暂时只有一人，记录这一限制；隔一段时间自我复核不能冒充独立双人标注。标注者尽量看不到方法名称与最终答案预测。标准支持集可能不包含所有替代证据，对“断链但答对”的样本需人工检查。

### 5.2 模型准备

| 用途 | 起始选择 | 本机执行方式 |
|---|---|---|
| 冒烟与主流程调试 | `Qwen/Qwen2.5-3B-Instruct-GGUF`，Q4_K_M | 先单请求运行，证据预算 512／1,024／2,048 token |

Qwen 官方 3B Q4_K_M 是单个文件；7B Q4_K_M 当前为两片，必须下载同一 revision 的全部分片。只下载选定量化版本，避免拉取整个含多种精度的仓库。[3B 模型](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct-GGUF)、[7B 模型文件](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-GGUF/tree/main)。3B 与 7B 的许可不同，应保留各自模型卡。两者同属一个家族，只能支持跨规模验证；若后期要声称跨模型家族有效，再加入另一家族的小模型。

Provence 的代码位于 **NAVER Bergen 仓库**的对应目录，不能按不存在的 `naver/provence` 仓库部署。[代码与实验配置](https://github.com/naver/bergen/blob/main/scripts/provence/readme.md)、[模型卡](https://huggingface.co/naver/provence-reranker-debertav3-v1)。模型涉及自定义代码，固定 revision 并检查加载代码；优先调用其独立接口，避免把 Bergen 的所有生成后端都装进来。[LLMLingua 官方代码](https://github.com/microsoft/LLMLingua)

模型选择旨在让本机可实施，不代表这些模型是当前最强模型。先用“完整参考支持”做少量诊断，判断阅读器能否完成目标推理：如果给足证据也经常失败，继续优化压缩很难产生可解释收益。参考支持只用于这一上限诊断，不能输入正式方法。

### 5.3 安装顺序与启动模板

执行顺序：保存硬件信息 → 创建独立 Python 环境 → 安装基础数据包 → 下载固定版本 llama.cpp → 下载 3B 单一量化文件 → 跑 10 次短问答 → 跑 30 题不同上下文长度的显存与时间测量 → 再装压缩器与评分模型。**本计划没有执行安装或修改显卡驱动。**

当前驱动为 560.94。优先检查兼容的 CUDA 12.x 发行包，例如发布页仍提供时的 12.4 构建；不要直接假设最新 CUDA 13.x 包可用。驱动要求、运行库和构建版本要一起核对。官方对 CUDA 次版本兼容也列有限制，不能只看显卡型号判断。[NVIDIA 兼容说明](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)

以下是**完成下载后**的启动模板，路径指向未来拟建的 `topic2` 目录，当前并不存在这些可执行文件或权重；它不是本轮已运行命令：

```powershell
& 'F:\llm_wiki_research\topic2\vendor\llama.cpp\llama-server.exe' -m 'F:\llm_wiki_research\topic2\models\qwen2.5-3b-instruct-q4_k_m.gguf' -c 4096 -np 1 -ngl 99 --host 127.0.0.1 --port 8080 --no-cache-prompt --cache-ram 0 --no-context-shift
```

这些参数按本轮 Context7 与官方 server 文档核验：限制上下文和单请求，关闭跨请求提示词复用，禁止上下文滑动。固定 release 的 `--help` 才是实际运行依据；旧版本参数不同需记录等效配置。[官方 server 文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)

先用 4,096 总上下文做 2,048 以内证据预算；测试 4,096 证据 token 时，总上下文需进一步增加，并为系统提示、问题、聊天模板和输出预留空间。超长样本应被标记或按预先定义方案处理，不能让服务静默截断。输出初始统一为简短答案、最大 128 token、确定性解码；发现正常答案截断时在开发阶段统一调整。

首个环境验收清单：GPU 确实参与计算；同一请求能重复运行；返回 token 计数可核对；最长输入不截断；缓存关闭后日志没有跨请求复用；CPU 评分和 GPU 生成的总耗时能够分别记录。权重加载不计入稳态单次查询，但单独报告启动时间。

## 六、系统结构与具体开发模块

[流程图可编辑源码](assets/topic2_plan/流程图源码.md)。正文采用图片，避免阅读器不支持 Mermaid 时显示源码。

| 模块 | 输入 → 输出 | 初版做法与验收 |
|---|---|---|
| M1 数据适配 | 官方文件 → 无标签输入、标签文件、来源映射 | 官方样例评分对齐；随机核对 20 条句序与跨度 |
| M2 基线装配 | 问题＋固定候选 → 预算内原文 | 段落、句子、邻句补全三种策略；最终文本可重建 |
| M3 依赖索引 | 仅原文 → 有向依赖边与置信度 | 规则识别明确别名／更名；局部指代需可定位前件；证据不足不强行绑定 |
| M4 多粒度证据包 | 核心句＋依赖 → 短包／长包 | 短包补齐高置信必要解释，长包取原段落；环依赖合并或有界处理 |
| M5 预算装配 | 包候选＋相关性＋预算 → 最终原文并集 | 贪心与局部替换起步；同一内容长短版本互斥；共享句子只计一次 |
| M6 视图物化 | 候选包＋训练期工作负载＋存储预算 → 视图目录 | 按预计使用价值和构建／读取成本选择；保留固定长度、频率优先对照 |
| M7 在线选择 | 当前问题＋可用视图＋来源版本 → 读取／扩展／回退计划 | 轻量覆盖估计＋实测代价查表；记录选择理由，不额外调用大模型规划 |
| M8 评测与日志 | 最终文本、答案、计时、标签 → 逐题指标与汇总 | 正式方法无法访问标签；报告失败与超时，不能只汇总成功样本 |

### 6.1 依赖抽取要做多复杂

从高精度规则开始，例如“X, formerly known as Y”“X was renamed Y”，并保存支持该关系的原文跨度。指代初版限制在相邻几句、明确可识别对象内；“最近的名词”只能作为候选，不能直接当真值。置信度阈值由开发标注确定。必要时用小模型辅助离线抽取，原文不能支持的边不进入硬约束。

避免一开始对全部语料做昂贵的大模型图谱抽取。先测 100／1,000 篇文档的单位成本、准确率和覆盖率，再决定是否扩展。若规则覆盖过低而模型抽取昂贵，应把这一事实写入阶段判断。

### 6.2 证据包如何形成

保留“核心句＋必要前件”的短表示和原段落长表示。按当前问题激活有关关系：所有有关系的句子并非都必须保留。跨文档前件不在固定候选池时，在质量隔离实验中标记无法补齐，不能悄悄从 Wiki 加进外部事实。

组合算法的最低规则：每次增加包，计算最终去重原文的新增长度；一个前件被多个包共享时只算一次；最终模板再计数，超预算则做完整包替换或回退，禁止直接裁掉末尾。保留原文内部顺序，跨文档采用固定排序规则。证据之间可能互补，不应未经证明宣称目标具有次模性或给出理论近似保证。

### 6.3 SQLite 中保存哪些内容

| 逻辑表 | 关键字段 |
|---|---|
| documents | document_id、source_uri、version_hash、title、raw_text |
| spans | span_id、document_id、start、end、official_sentence_id |
| dependencies | dependent_span、required_span、type、confidence、support_span |
| views | view_id、variant_group、variant、tokenizer_revision、token_count、build_cost、valid |
| view_spans | view_id、span_id、order；保存成员与出处 |
| view_sources | view_id、document_id、version_hash；用于失效判定 |
| workload_stats | 训练期／已到达请求的访问统计，不含未来题目 |
| query_runs | run_id、query_id、plan、span_ids、tokens、times、status |

同一源句正文优先只存一份，视图保存成员与排序；若为了读取速度再物化拼接文本，额外占用必须记入总存储。索引也计费，不能只报告压缩文本大小。初期给实体 ID、来源版本和视图成员建立普通索引即可，不把“使用 SQLite”本身写成创新。

### 6.4 代价模型与来源更新

先在开发数据采集读取字节数、候选包数、输入 token、CPU 选择时间、模型输入处理时间。用分桶均值或简单回归估计三种方案的时间；加入覆盖不足与低置信关系的惩罚，门槛在开发阶段锁定。代价模型按当前硬件校准，不能拿别人的 GPU 延迟作真值。

来源更新后，利用 document_id 与 version_hash 找到受影响视图，先使其失效，随后重建。第一版做这一正确性即可，不必立即实现复杂增量传播。若测试更新造成答案变化，必须同步更新标签并人工核对；没有更新标签的扰动，只用于失效机制测试。

## 七、实验分层、基线与比较条件

### 7.1 先隔离质量，再测试完整查询

**实验 A：固定候选池的压缩与装配。** 各方法访问同一原文范围、同一生成器、同一提示与排序协议。比较 512／1,024／2,048／4,096 证据 token；本机先做前 3 档。只改变保留与装配策略，判断依赖保护是否有效。

**实验 B：视图复用与在线整理。** 固定原始候选池或其获取方式，比较有无物化和不同视图选择策略；查看省下了多少依赖抽取／压缩时间。此阶段若没有改变检索环节，就不能声称向量检索更快。

**实验 C：允许视图优先访问的完整系统。** 开放“查视图—必要时回原文”的路径，报告候选召回、视图适用判断错误、回退与最终质量。它与实验 A 的成绩单列，避免把新增检索能力当成压缩算法收益。

### 7.2 对照矩阵

| 编号 | 基线／变体 | 必须控制的细节 |
|---|---|---|
| B0 | 给定候选直接输入，不做语义压缩 | 超出模型上下文时不称“完整输入”；注明覆盖比例与处理规则 |
| B1 | 相关性段落选择／句子选择 | 按实际 token 预算，不能简单拿相同段落数代替 |
| B2 | 强句级评分＋相邻句补全 | 在开发集选择前后窗口，不用故意弱的固定窗口 |
| B3 | Provence | 调节阈值使实际预算可比；记录联合重排是否启用 |
| B4 | LLMLingua-2 | 固定发布权重与压缩配置；记录实际保留正文及对齐限制 |
| B5 | 普通证据缓存＋相同压缩器 | 与本方法同存储额度、预热与失效规则；不缓存最终答案 |
| B6 | 固定长度／频率优先的精简视图 | 隔离“只要提前做就会快”的通用收益 |
| B7 | SPARE-RAG、SpectRAG 或其可说明的适配版 | 重点查重基线；代码、预算和候选范围不能一致时单列限制 |
| Ours | 依赖保持＋多粒度视图＋代价选择 | 每个新增模块均有消融，不能只报全部叠加后的结果 |

Provence 与 LLMLingua-2 的官方代码／模型入口已核验，但未在本机运行。SPARE-RAG 前期资料声明代码与检查点仍在整理；本轮页面访问受限，**未核实是否已有新发布**。第 2 周重新核对，拿不到代码则依据论文明确重实现范围，不把简化版冒充原方法。SpectRAG 同样先登记可获得代码、依赖与改动。RECOMP 作为资源允许后的补充基线。完整系统框架不必都在第一周复现。

计划冻结前至少建立“模块重叠表”：每个最近工作是否包含句级依赖、预算选择、物化复用、来源失效、在线代价选择。当前已有类似工作不意味着题目不能做，但“首次保护证据链”“首次把数据库优化用于 RAG”不能作为创新声明。[SPARE-RAG](https://doi.org/10.3390/info17101052)、[SpectRAG](https://arxiv.org/abs/2610.36991v3)、[SSC](https://www.amazon.science/publications/safe-and-sufficient-caching-per-request-validated-evidence-reuse-for-production-retrieval-augmented-generation)、[SemReuse](https://arxiv.org/abs/2610.16035)、[PlanRAG](https://arxiv.org/abs/2607.00508)

### 7.3 必做消融

分别移除：依赖约束；多粒度选择（只留原段落）；视图物化（逐次计算）；代价选择（固定短视图）；Wiki 关系层（原文同类抽取）。另外与“Provence＋普通缓存”比较，检验收益是否只是已有模块叠加。

人工机制实验：对已确认需要更名／前件的样本，删除该片段，并另删相近长度的无关片段作为配对对照。以数据集上的多例表现检验关键联系作用，不用单个虚构例子代替证据。

## 八、查询工作负载、计时和评价指标

### 8.1 工作负载必须包含不利情况

使用三个独立报告的序列：W0 全新自然问题；W1 同实体或共享证据但答案要求不同的自然问题；W2 人工加入重复／改写的受控序列。W2 可从 0%、25%、50% 的重复率起步，另设高复用压力测试，但不能用它代表自然用户分布。一个问题的改写与原问题归同一族。

每种序列预先固定到达顺序，并至少用 3 个顺序种子重复。每次开始清空应用层查询缓存；离线编译的静态视图允许存在，但必须计入构建成本。**静态视图已建但查询缓存为空**、**访问后预热的应用缓存**、**操作系统文件缓存**、**模型跨请求 KV 缓存**是不同状态，日志必须区分。

### 8.2 指标定义

| 指标 | 计算对象与口径 |
|---|---|
| 答案 EM／F1 | 沿用官方归一化与答案别名；以简短答案为主要输出，引用评估另做 |
| 完整支持集保留率 | 标准支持所需的实际文本是否全部进入最终输入；仅保留来源 ID 不算 |
| 压缩断链率 | 在候选池已含完整参考支持的条件下，压缩后丢失必要支持的比例；同时报分母 |
| 语义依赖错误率 | 人工子集上的缺前件、错绑定、误保留；与一般句子保留率分开 |
| 输入 token | 原文证据与总 prompt 各报一份，用生成器实际 tokenizer／服务计数 |
| 查询首 token 时间 | 从收到问题到客户端收到首个非空生成内容，包含检索、装配与模型处理 |
| 服务首 token 时间 | 从发出模型请求到首个非空生成内容，用于区分前置处理开销 |
| 端到端时间 | 从问题到完整答案，报告均值、P50／P95和分阶段耗时 |
| 复用与回退 | 视图命中、适用判断失败、扩展率、回退率、回退额外时间 |
| 全成本 | 离线构建时间、总磁盘与内存、在线累计耗时、来源更新代价 |

LLMLingua-2 可能删到词级，不能只用“原句 ID 被选中”认定支持完整。自动统计严格原文跨度保留，另在人工作业子集检查语义是否仍足够；不把严格逐字保留直接等同于推理能力。MuSiQue 的支持段落 ID 尤其不能代替跨度评估。

### 8.3 笔记本计时协议

固定供电与性能模式，记录温度、GPU 利用率及实际空闲显存。正式测量期间避免同时进行大下载、视频渲染或其他模型推理。单并发为主，先 20 次热身，再计时；方法运行顺序按区组交替，降低温度漂移的偏差。每条查询仍保留独立时间，不能只用整个脚本总时间相除。

第一组公平实验关闭所有方法的跨请求 prompt／KV 复用；第二组可以共同开启，检验本方法与通用推理缓存是否互补。通过 `cache_n` 或所选服务版本的等效字段验证是否真的复用。服务返回的 `prompt_ms` 是模型内部输入处理指标，**不能替代客户端端到端时间**。[llama.cpp 计时与缓存说明](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)

如果为了批量生成先把所有上下文离线算好，这批运行只能评估质量和生成时间；在线检索、压缩与选择耗时必须另测，最终再重跑真实完整查询才能声称端到端加速。CPU 压缩器是本机起点，要明确这一硬件分配；若显存允许，还需小规模验证较强 GPU 压缩配置，防止速度优势仅来自基线被迫放在 CPU。

记录超时、OOM、无效输出和回退，设置统一重试／失败规则。不要自动忽略失败样本，也不要只给表现不好的基线更短超时。断点恢复可以复用已完成的质量结果，但延迟实验必须标明是否跳过了实际计算。

### 8.4 统计与成本回本

答案质量按题做配对 bootstrap，报告 F1 差值与 95% 置信区间。重复／改写工作负载按问题族或序列区块重采样，不能把同一题的多个改写当完全独立样本。主比较、主预算和质量容忍范围在开发阶段确定；其他预算与分组作为补充，避免挑最好的一格。

效率主张采用两种互补比较：同预算比较质量；在开发集确定的接近质量配置下比较速度，并在冻结数据验证。可将“不低于强基线超过 1 个 F1 绝对百分点”作为待确认的初始容忍范围，但正式判断应检查差值区间下界，而非只看点估计接近。

累计成本用普通文字公式记录即可：**总时间＝离线构建时间＋全部在线查询时间＋更新维护时间**。仅在单位查询节省稳定且为正时，才可用“离线额外时间÷平均每题节省”估计回本次数；频繁更新和非平稳工作负载应直接画累计曲线。存储节省与输入压缩分开报告，因为增加视图可能使数据库更大。

## 九、本机实验规模、运行预算与降级方案

先用 30 题测每个方法的真实时间。第一轮主表可采用：2 个数据集 × 每集 1,000 题 × 6 个主方法 × 3 档预算＝**36,000 次答案生成**，第二模型只对最关键的 3 个方法、1 档预算做 1,000 题／集验证，另需 6,000 次。无压缩参考若与预算无关只运行一次，不必复制成多个预算实验。

这些只是计算量核算，不要求一次全部执行。假设实测平均每次 5 秒，36,000 次仅生成就约 50 小时；若为 15 秒则约 150 小时，尚不含整理、失败和读写。**这两个时间是假设示例，不是本机性能测量。** 根据实际中位数与长尾重新排期。

建议分三档推进：

| 档位 | 范围 | 能回答什么 |
|---|---|---|
| 冒烟 | 每集 100 题，3 方法，2 预算，3B | 流程是否正确，指标和 token 是否可信 |
| 预实验 | 每集 500 题，5 方法，3 预算 | 是否有继续投入的信号；不能据此宣布普遍有效 |
| 正式 | 预先冻结的每集至少 1,000 题，6 主方法，3 预算；再补关键基线、消融与第二规模 | 支撑明确限定范围的论文结论；按功效与资源扩大 |

预留 30–60 GB 项目空间是初期工作估计，覆盖选定模型、数据、日志与快照；以下载清单实际大小为准。保留原始结果，但不要默认保存每一步完整概率矩阵或反复复制模型。

显存不足：先固定较短总上下文与单并发；再用较小阅读器或固定 offload；不得只对某个方法偷偷减少证据预算。CPU 评分过慢：先缓存与问题无关的文档向量、批量编码，不能预先计算测试问题相关的分数后声称在线免费。样本依赖过少：先确认数据适配与定义，再考虑扩大自然样本或调整问题，而不是人为插入大量更名句构造主结果。

## 十一、继续、收缩或转向的判断条件

**关口 G1，第 3 周：问题是否真实存在？** 在自然样本中有可复核的依赖损伤，且它不是全部来自候选检索遗漏、分句错误或阅读器本身无能力。若只在人工编造例子中出现，先暂停复杂系统开发。对罕见现象可以研究，但需说明覆盖范围与足够的自然样本支持。

**关口 G2，第 5 周：简单方法是否已经足够？** 调优的邻句窗口和强压缩器必须比较。如果本方法无法在相同预算改善质量或显著减少依赖错误，应检查识别误差，或收缩成明确子问题；不能靠加长输入制造优势。

**关口 G3，第 8–9 周：加速是否超过通用缓存？** 与“同一压缩器＋普通缓存”比，若收益完全由预计算解释，方法贡献不足。若只在高重复查询中有效，明确定位为高复用负载，不声称适合任意查询。

**关口 G4，正式实验：结果是否支持原主张？** 更短但更慢，只能报告压缩收益；更快但质量下降超过约定范围，只能报告速度—质量折中；依赖保留更好但答案不变，需要分析阅读器能力、替代证据或标注不完备。负结果同样保留，不通过测试集反复调参“修成正结果”。

预实验可把“两个数据集多个紧预算点有一致方向”“总时间确实下降”“增益超过测量噪声”作为继续依据。具体增益大小由数据决定，本计划不承诺论文录用或固定提升倍数。
