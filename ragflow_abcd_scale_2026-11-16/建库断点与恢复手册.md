## 2. 保存位置与校验

原工作区仍保有实验目录和原始 WSL 磁盘。恢复时优先使用原工作区和原 WSL 实例。冷备保存在 `F:\llm_wiki_research\output\checkpoints\ragflow-abcd-scale-2026-11-16`。

| 文件 | 内容 |
| --- | --- |
| `ragflow-wsl-ext4.vhdx` | `LLMWikiRAGFlow` 的停机磁盘副本，包含已下载的 Docker 镜像、容器状态和五个持久卷。MySQL 保留知识库和合并队列元数据，Elasticsearch 保留已经写入的原文和 Wiki 索引，MinIO 保留原文对象，Kvrocks 和 NATS 保留各自的持久状态。 |
| `vhdx-manifest.json` | VHDX 文件大小、SHA-256、源与副本一致性校验结果。 |
| `experiment-files.zip` | 冻结题目、候选语料、已编译原句关系、流水线配置、日志、脚本、官方评分实现、分词器和选定的平台配置。路径相对 `F:\llm_wiki_research`。 |
| `experiment-files-manifest.json` | ZIP 大小、SHA-256、文件数量和归档 CRC 校验结果。 |

冷备和原数据位于同一 F 盘，可用于恢复原文件误改或服务数据异常。若需覆盖硬盘整体故障，把整个备份目录另存到另一物理磁盘。VHDX 含原实验平台的本地认证状态，应按实验私有数据保管。ZIP 的恢复前提包括原工作区的 Python 运行环境 `topic2\.venv`、平台目录的本地凭据文件和 `release/docker/.env`，以及有效的 `DASHSCOPE_API_KEY` 环境变量。ZIP 未收录这些凭据。

校验备份时可在 PowerShell 执行以下命令，并与两个清单比较。

```powershell
Set-Location -LiteralPath 'F:\llm_wiki_research\output\checkpoints\ragflow-abcd-scale-2026-11-16'
Get-FileHash -Algorithm SHA256 -LiteralPath 'ragflow-wsl-ext4.vhdx','experiment-files.zip'
Get-Content -LiteralPath 'vhdx-manifest.json','experiment-files-manifest.json'
```

若原 WSL 磁盘损坏，先校验备份，再把 VHDX 复制到单独的恢复目录，以不同的 WSL 名称用 `wsl --import-in-place <恢复实例名> <可写副本的绝对路径>` 注册工作副本。保留冷备文件本身。原实例与恢复实例使用相同容器端口和宿主机挂载路径，同一时间只启动其中一个。在下节命令里将 `LLMWikiRAGFlow` 换成恢复实例名。恢复时用 ZIP 补齐缺失的实验文件，保留原来的工作区路径和现有凭据，并核对下节的数据集 ID。冷备已做文件级校验，恢复实例的启动及云端续跑留待实际恢复时验证。

## 3. 在原数据集接着建库

### 启动依赖并确认代理地址

1. 从原实验目录操作。确认百炼有可用额度，两种冻结模型 `qwen3.5-plus-2026-04-20` 与 `text-embedding-v4` 各用一次最小测试分别返回 HTTP 200。维护本地代理时，凭据从 `DASHSCOPE_API_KEY` 和既有 `relay-token.local` 读取。
2. 启动专用 WSL 的 Docker 守护进程，再启动原有依赖容器。以下命令仅在计划恢复时运行。

```powershell
wsl -d LLMWikiRAGFlow -u root -- sh -lc 'docker info >/dev/null 2>&1 || (nohup dockerd >/var/log/dockerd-topic2.log 2>&1 </dev/null & sleep 4)'
wsl -d LLMWikiRAGFlow -u root -- docker start topic2-ragflow-mysql-1 topic2-ragflow-es01-1 topic2-ragflow-minio-1 topic2-ragflow-kvrocks-1 topic2-ragflow-nats-1
wsl -d LLMWikiRAGFlow -u root -- docker ps --format '{{.Names}} {{.Status}}'
wsl -d LLMWikiRAGFlow -u root -- ip -4 route show default
wsl -d LLMWikiRAGFlow -u root -- ip -4 addr show dev eth0
```

3. 检查 Windows 侧 WSL 网关地址和 WSL `eth0` 地址。断点时分别是 `172.18.96.1`、`172.18.98.228`。端口 `17892` 已有可用的代理时继续使用；否则从实验目录重启代理。命令的前两个地址按实际结果填写。

```powershell
Set-Location -LiteralPath 'F:\llm_wiki_research\ragflow_abcd_scale_2026-11-16'
& ../topic2/.venv/Scripts/python.exe -X utf8 -u ragflow_model_relay.py 172.18.96.1 172.18.98.228 ../topic2/platform/ragflow-1.0/relay-token.local logs/ragflow-model-usage.jsonl --port 17892
```

4. 依赖容器健康后启动原应用和两个原有的额外 ingestor。查看 `19380` 端口，未登录探针收到 HTTP 401 表示 API 已可达。若冷启动遇到历史 `host-gateway` 解析错误，使用本实验目录的 `compose-wsl-host.yml` 和原平台的 `compose-experiment.sh` 重建应用容器，保留上述持久卷。

```powershell
wsl -d LLMWikiRAGFlow -u root -- docker start topic2-ragflow-ragflow-cpu-1
wsl -d LLMWikiRAGFlow -u root -- docker exec -d -w /ragflow topic2-ragflow-ragflow-cpu-1 bin/ragflow_server --ingestor --ingestor-concurrent-workers 24
wsl -d LLMWikiRAGFlow -u root -- docker exec -d -w /ragflow topic2-ragflow-ragflow-cpu-1 bin/ragflow_server --ingestor --ingestor-concurrent-workers 48
curl.exe --noproxy '*' --max-time 3 -s -o NUL -w '%{http_code}' http://127.0.0.1:19380/api/v1/users/me
```

如果 Windows 侧网关地址变了，在现有的 RAGFlow 模型服务实例 `topic2-dashscope-relay` 中只修改 Base URL，保留原模型记录及其 ID。下面的 `native --relay` 使用相同的新地址。`run_scale.ps1` 目前按断点时的地址调用 `native`，如地址变化，用下列分阶段命令衔接。

### 续跑同一个知识库

先检查 `data/native-full.json` 中的数据集 ID 与本手册一致，并确认 API 能按该 ID 找到原知识库及全部 6,752 份文档。在实验目录执行下列只读核对。

```powershell
@'
import json
from pathlib import Path
from ragflow_native_setup import authenticate

saved = json.loads(Path('data/native-full.json').read_text(encoding='utf-8'))
dataset = saved['dataset_id']
client = authenticate()
assert client.call('GET', f'/datasets/{dataset}')['name'] == 'topic2-native-wiki-scale-500-20261116'
assert client.call('GET', f'/datasets/{dataset}/documents', params={'page_size': 1})['total'] == 6752
print('Restored dataset and document count verified:', dataset)
'@ | & ../topic2/.venv/Scripts/python.exe -X utf8 -
```

核对通过后执行以下命令，只完成原文入库与原生 Wiki 合并。若网关改变，将 `--relay` 替换为上述配置的新地址。

```powershell
& ../topic2/.venv/Scripts/python.exe -X utf8 -u scale_pipeline.py native --relay http://172.18.96.1:17892/v1
```

正常续跑会核对现有文档 ID，通常输出 `uploading 0 missing documents of 6752`，把处于可重试状态的未完成文档重新排队。现有冻结划分和 `data/compiled.jsonl` 继续使用。用以下日志确认完成数是否上涨，及合并的 `inflight`、`backlog` 是否逐步清空。若持续出现账户 `Arrearage`，停止原应用容器以免 Wiki 后台反复请求，并保留数据卷。若怀疑旧任务租约滞留，可用平台的 `check-compile-queue.sh <数据集 ID>` 只读检查。历史的 `--requeue-stale-claim` 修复专用于恰有 32 条特定旧任务的情况，当前应按实际队列状态诊断。

```powershell
Get-Content -LiteralPath 'data/native-full-progress.jsonl' -Tail 10
Get-Content -LiteralPath 'logs/ragflow-model-usage.jsonl' -Tail 10
```
